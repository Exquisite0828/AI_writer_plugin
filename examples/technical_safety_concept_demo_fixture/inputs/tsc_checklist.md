# TSC Review Checklist

- Each TSR has a unique identifier.
- Each TSR traces to a project source functional safety requirement and safety goal.
- Each TSR has an architecture allocation or an explicit open item.
- Each safety mechanism links to a TSR or safety goal and has a consistent allocation.
- Fault tolerance time values (FTTI/FDTI/FHTI) come from a project source or remain open; they are tabulated, not implied in prose.
- Safe state definitions are consistent with the HARA summary, or differences are recorded.
- Each ASIL value comes from a project source or human confirmation.
- Each verification method is marked as proposed unless confirmed by source or HITL.
- TSR statements are technical and verifiable, not a restatement of the functional safety requirement wording.
- Samples are never used as project facts.
- References are not used to prove project-specific TSR, mechanism, ASIL, allocation, or approval.
- Requirement completeness and sufficiency are not approved without human confirmation.
- The final report remains a review package, not a professional approval or compliance approval.
- HSC content, SSC content, and detailed hardware or software implementation remain out of scope.
